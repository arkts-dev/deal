# DEAL v1.2 Conformance Promotion Gate (ISSUE-0107)

`fs/docs/spec-v1.2.md` is the only language spec for DEAL v1.2. v1.1 source
compatibility is not preserved: rest parameters, top-level executable
statements, imports after declarations, and nested exports are removed, `int`
becomes signed 32-bit, and `bytes` plus the C FFI declaration surface
(`// @deal-version`, `// @extern-c`, `// @c-struct`, `// @c-pointer`) are added.

This document records how the conformance gate enforces the promotion and
which v1.2 cases remain intentionally unsupported (each with an explicit
failing fixture and a tracked follow-up issue).

## The three gates

| Gate | Runner | Must hold |
|---|---|---|
| Frontend conformance (v1.2 grammar and semantics) | `deal.test.ConformanceTest` over `test/conformance/frontend/` | every fixture passes; 0 failed; 0 skipped |
| LuaJIT backend-runtime conformance (v1.2) | `deal.test.ConformanceTest` over `test/conformance/backend-runtime/` (real LuaJIT execution) | every fixture passes; 0 failed; 0 skipped |
| JVM backend-runtime conformance (v1.2) | `deal.test.BackendConformanceTest` (`test/conformance/fixtures/*.json`, `backends: ["jvm"]`) plus `deal.test.JvmBackendTest` | every JVM-applicable case passes; 0 unclassified skips |
| JVM corpus conformance promotion (ISSUE-0102 origin — ISSUE-0168 capability accounting) | `deal.test.JvmConformanceTest` over `test/conformance/backend-runtime/` (real CompilationOrchestrator → JvmBackend → javac → java) | zero applicable failures AND ≥80% of the unchanged 255-test backend-runtime denominator passes on JVM; frontend-classified files 100%; every skip carries a reason and a gap id; zero stale skips; zero probe runner exceptions |

All three runners execute from `./run_tests.sh`, which must exit 0.

Until the ISSUE-0237 resolution lands its disposition pair, the LuaJIT
backend-runtime gate additionally records one tracked staged failure
(`stdlib-edge/time-now-millis-positive.deal`, locked E8004 artifact) — a
non-fatal interim state the runner verifies every run; any drift fails the
gate (see Classification contract).

## Classification contract

Every `.deal` file under `test/conformance/` carries an explicit
classification. There are no unclassified skips:

- a file without `@expected`, with an unknown `@expected` value, or with a
  `@spec` reference that does not start with a v1.2 spec section is a
  **classification failure** and fails the gate;
- `compile-ok` / `compile-error CODE` — frontend-only expectations;
- `runtime-ok` / `runtime-error CODE` — compile plus real LuaJIT execution;
- `companion` — classified support module (`*_lib` fixtures) that must keep
  compiling standalone; `.d.deal` companions run the declaration-file
  pipeline (`ExportExtractor`);
- `host-fixture` — reserved for `test/conformance/host-fixtures/*.d.deal`
  (discovery skips that subtree; the classification is documented in each
  file);
- `known-fail MODE` — an explicit failing fixture for an intentionally
  unsupported v1.2 case, with a mandatory `@issue` tag.

The `known-fail` mechanism is the promotion driver: the runner executes the
underlying expectation and records the case as a non-fatal tracked
known-failure while the requirement is unsatisfied. As soon as the tracked
issue lands and the fixture starts passing, the gate **fails with a
promotion instruction** (remove the `known-fail` marker and set the real
`@expected`), so v1.2 promotion is forced instead of silently forgotten.
The JSON backend fixtures use the same mechanism via the `"knownFail"` field.

### Staged failures (design-sanctioned interim states)

A staged failure is a fixture whose own expectation is temporarily
unsatisfied by a locked artifact whose disposition is owed by another
child; it is tracked by the runner's staged-failure registry, never by a
fixture `@expected` value. The runner executes the fixture, verifies that
the locked artifact code is still produced, and records the case as a
non-fatal `STAGED-FAIL` naming its owning issue. The registry is
validated against the on-disk corpus every run, and an entry that becomes
stale fails the gate with a promotion instruction (remove the registry
entry) — the staged state can never silently rot.

- `test/conformance/backend-runtime/stdlib-edge/time-now-millis-positive.deal`
  — `STAGED-FAIL` (`runtime-ok` blocked by the locked E8004 artifact;
  tracked by ISSUE-0237). The retained `std/time.nowMillis ()->int` route
  computes `os.time() * 1000` (≈1.7e12 for contemporary epoch
  milliseconds), which deterministically raises E8004 under the
  signed-int32 gate landed by ISSUE-0332. The fixture keeps its
  `runtime-ok` expectation and `std/time.lua` stays frozen until the
  delegated time-selector child lands exactly one disposition pair
  (`luajit-v1.2-stdlib-contracts` D6,
  `luajit-v1.2-conformance-retirement-and-gate` D3). When the owning
  child lands its disposition — the fixture starts passing, or its
  expectation changes — the gate fails with a promotion instruction to
  remove the registry entry.

## Intentionally unsupported v1.2 cases

### `int` signed 32-bit semantics — ISSUE-0111

- `test/conformance/frontend/lexer/int32-literal-out-of-range.deal`
  — `known-fail compile-error E1036` (literal `2147483648` outside the
  unary-minus position must be a compile-time error).
- `test/conformance/fixtures/jvm-v1.2-known-fail.json`
  (`jvm-int32-literal-out-of-range`, `jvm-int32-add-overflow`) — JVM gate.

The LuaJIT-owned `backend-runtime/arithmetic/int-add-overflow.deal` was
promoted to `runtime-error E8004` with the signed-int32 runtime gate
(ISSUE-0332), alongside the new `int-sub-overflow`, `int-mul-overflow`,
`int-conversion-out-of-range`, and `source-location/int32-overflow-source`
fixtures. Passing fixtures pin the v1.2 boundary shapes already:
`frontend/lexer/int32-literal-max.deal` and
`frontend/lexer/int32-literal-min-via-unary-minus.deal`.

### `bytes` — ISSUE-0111

- `test/conformance/frontend/types/bytes-type-reference.deal`
  — promoted to `compile-ok` with the JS bytes lane (ISSUE-0322): the
  checker resolves the `bytes` primitive, the `bytes(n)` intrinsic, byte
  index reads/writes, and the compiler-resolved `.length`.
- `test/conformance/backend-runtime/bytes/bytes-buffer-ops.deal`
  — promoted to `runtime-ok` with the LuaJIT bytes emitter slice
  (ISSUE-0339): `bytes(n)` lowers to `__rt.bytes_new`, `b.length` /
  `b[i]` / `b[i] = v` lower to the bytes runtime entries with span
  arguments, and the bytes write emits the single-evaluation sequence
  (receiver and index once each, RHS after them, write validation after
  the RHS). The promotion landed alongside the new bytes fixture family:
  `bytes-index-bounds` (E8012), `bytes-write-range` (E8013),
  `bytes-length`, `bytes-descriptor-boundary` (canonical `[bytes]`,
  `?bytes`, `(bytes)->bytes`, `[?(bytes)->bytes]` descriptors with real
  bytes values), `bytes-class-field-descriptor`,
  `bytes-write-single-evaluation`, and `bytes-write-validation-order`
  (runtime-ok), plus the source-location pins
  `source-location/bytes-index-bounds-source` and
  `source-location/bytes-write-range-source`. Unary int negation routes
  through the checked gate in the same slice: `arithmetic/int-neg-min`
  (E8004 from `-(-2147483648)`) and
  `source-location/int-neg-min-source` pin the location.
- `test/conformance/fixtures/jvm-v1.2-known-fail.json` (`jvm-bytes-buffer-ops`)
  — JVM gate; the LuaJIT-owned bytes fixtures are JVM-classified under
  `JVM-GAP-BYTES` until the JVM bytes lane lands (ISSUE-0277).

### Compiler directives and C FFI — ISSUE-0111

- `test/conformance/frontend/lexer/unknown-directive-rejected.deal`
  — `known-fail compile-error any` (an unrecognized directive name must be a

- `test/conformance/frontend/modules/c-struct-invalid-field-rejected.deal`

- Passing shape pin: `frontend/modules/deal-version-directive.deal`

### v1.2 frontend hard break (removed v1.1 forms) — landed

The v1.2 grammar gates are landed across the pipeline: the parser rejects
`...` rest parameters in parameter lists and function types (E1047, with
recovery parsing retained); the post-parse module shape validation
(`deal.module.ModuleShapeValidator`, run by `CompilationOrchestrator` and
mirrored by the JVM test harnesses) rejects imports after a top-level
declaration (E1048), module-level executable statements (E1049), nested
imports/exports (E1050), and bodyless declarations in implementation files
(E1051); and the orchestrator's selected-entry rule requires an exported
non-async `main(): null` (E2010 for a missing main, E2011 for an async or
wrong-signature main). The backend entry gates raise E6003 (rest backstop,
Lua backend) and E6004 (entry backstop, both backends).

- `test/conformance/frontend/functions/rest-param-declaration-rejected.deal`
  — `compile-error E1047`.
- `test/conformance/frontend/functions/rest-param-function-type-rejected.deal`
  — `compile-error E1047`.
- `test/conformance/backend-runtime/functions/rest-params.deal`
  — `compile-error E1047` (backend-runtime corpus).
- The remaining ISSUE-0103 tracking fixtures
  (`frontend/parser/top-level-let-rejected.deal`,
  `frontend/parser/import-after-declaration-rejected.deal`,
  `frontend/parser/nested-export-rejected.deal`) stay `known-fail
  compile-error any`: the frontend-only harness does not run the post-parse
  shape pass, so they remain tracked until that harness routes them through
  `ModuleShapeValidator`. The E1048/E1049/E1050/E1051 shape gates
  themselves are pinned by `ModuleSystemTest` (unit) and by the JVM gate
  fixtures (`jvm-modules-slice.json`, `jvm-skeleton.json`,
  `jvm-classes-slice.json`, `jvm-functions-slice.json` — the v1.1
  module-level shapes now pin `compile-error E1049`).

The v1.1 rest-parameter fixtures were removed or converted from the corpus
(the `host-rest-*` host-ABI fixtures became fixed-array E8010 boundary
fixtures with the `host-fixtures/rest_join.{d.deal,lua}` host module, and
the `function-type-array-param`, `fixed-params-mixed`, and
`function-type-descriptor-array-param` entries of
`test/conformance/fixtures/type-descriptors.json` were retargeted to the
fixed-array shapes — the v1.2 runtime type descriptor format has no
rest-parameter form) because rest parameters do not exist in v1.2. The
`@spec` references of the whole corpus were migrated onto v1.2 section
headings (`Modules — X` → `Modules, declarations, standard library, and
host ABI — X`; `Lua backend ABI — X` → `Runtime execution model — Lua
backend ABI — X`; `String escapes and UTF-8` → `String escapes and
Unicode`). The test harnesses that write a project manifest now declare
`languageVersion` `"1.2"` (`BackendConformanceTest`, `JvmBackendTest`,
`ModuleSystemTest`).

### Unicode scalar-value strings — ISSUE-0105 (LuaJIT, landed) / ISSUE-0106 (JVM, landed)

ISSUE-0106 landed the scalar-value string semantics in the JVM backend and
runtime: `std/string` length/substring/split measure Unicode scalar values,
string for-of iterates one scalar value per step, string ordering follows
scalar-value order, and strings crossing the host boundary (plus the `$check`
seam) reject unpaired UTF-16 surrogate code units (E8001/E8010). The passing
pins live in `test/conformance/fixtures/jvm-v12-slice.json`
(`jvm-v12-std-string-scalar-length`, `jvm-v12-std-string-scalar-substring`,
`jvm-v12-std-string-split-empty-scalar`, `jvm-v12-forof-scalar-iteration`,
`jvm-v12-boundary-string-supplementary`, `jvm-v12-scalar-compare-supplementary`)
and `test/conformance/fixtures/jvm-host-abi-slice.json`
(`jvm-host-bad-return-unpaired-surrogate`,
`jvm-host-nullable-return-unpaired-surrogate`,
`jvm-host-async-completion-unpaired-surrogate`). The promoted
`jvm-unicode-scalar-string-length` case left `jvm-v1.2-known-fail.json`.

MR-0107 (ISSUE-0105) landed the same semantics in the LuaJIT backend and
runtime: `std/string` length/substring/split measure Unicode scalar values
(byte offsets derived via `__rt.utf8_next`), string for-of iterates one
scalar value per step, and host-returned strings carrying malformed UTF-8
or encoded surrogate code points are rejected at the boundary (E8010). The
two previously tracked LuaJIT known-fail fixtures
(`test/conformance/backend-runtime/control-flow/for-of-unicode-scalar.deal`,
`test/conformance/backend-runtime/stdlib/string/string-length-unicode-scalar.deal`)
were therefore promoted to `runtime-ok`; the passing LuaJIT pins live in
`for-of-string-unicode.deal`, `length-unicode.deal`, `substring-unicode.deal`,
`host-invalid-utf8-e8010.deal`, and `host-surrogate-utf8-e8010.deal` (with
the `host-fixtures/bad_string` host module).

## JVM corpus promotion gate (ISSUE-0102 origin — ISSUE-0168 capability accounting)

`deal.test.JvmConformanceTest` runs every existing backend-runtime
conformance test through the real whole-project pipeline (module
discovery → frontend → `JvmBackend` codegen → `javac` → `java`) with a
deterministic applicability policy:

- frontend-classified files (`compile-ok` / `compile-error`) run the
  shared frontend pipeline and must pass 100%;
- companions compile as part of their importing tests' module graphs
  (never counted separately);
- known-fail fixtures run through the pipeline and stay tracked while
  their underlying mode fails (a stale marker fails the gate with a
  promotion instruction);
- backend-runtime tests are JVM-applicable unless the explicit skip
  registry classifies them. Every skip carries a documented reason and
  a gap id. The ISSUE-0168 capability-accounting re-audit promoted 50
  previously-skipped cases (the async-await and @jsonable slices that
  landed after the ISSUE-0102 gate, plus `async-cross-module` via the
  explicit-`.deal` companion alias fix) and classified the 34 remaining
  failures under the active gap ids, each probed through the real
  pipeline every run:
  - `JVM-GAP-STDJSON` — std/json JVM boundary: `JvmBackend` E6000 at
    `import std/json` (12 tests);
  - `JVM-GAP-JSONABLE-RESIDUAL` — residual @jsonable JVM defects
    (4 tests);
  - `JVM-GAP-HOST-ABI-SHAPES` — JVM host ABI unsupported declared
    shapes (12 tests);
  - `JVM-GAP-XMOD-FNVALUE` — cross-module function values (5 tests);
  - `JVM-GAP-XMOD-ARRAY` — imported async array return (1 test);
  - `JVM-GAP-ASYNC-FNEXPR` — async function expressions and block-level
    async functions (2 tests);
  - `JVM-GAP-DESCRIPTORS` — the canonical descriptor cutover's E8010
    signature-mismatch expectation (1 test, ISSUE-0336);
  - `JVM-GAP-INT32` — the signed-int32 E8004 expectations the JVM
    backend's retained ±(2^53−1) safe range cannot satisfy, including
    the unary-negation fixtures ISSUE-0339 added (8 tests);
  - `JVM-GAP-BYTES` — the LuaJIT bytes expectations (zero-fill buffers,
    E8012/E8013, single-evaluation writes, canonical bytes descriptors)
    until the JVM bytes lane lands (10 tests, ISSUE-0339/ISSUE-0277).

The registry is validated against the on-disk corpus (a stale or dead
entry fails the run); there is no fallback skip branch, and a skip that
starts passing fails the gate with a promotion instruction (remove the
registry entry) — the same forced-promotion rule that stale known-fail
markers carry. The gate requires zero applicable failures AND at least
80% of the on-disk backend-runtime denominator to pass on JVM (230/282
= 81.6% with the ISSUE-0339 fixture additions: 230 applicable passed, 0
failed, 52 classified skips, 0 tracked known-fails — the counts are
asserted by the runner's summary gates, not hardcoded).

The backend work the gate drove (ISSUE-0102): C-style `for` loops,
array `for-of`, `break`/`continue`, `try`/`catch`/`throw` with the
builtin `Error` reified as `DealError`, `delete`/`has()` for tables and
optional class fields (presence flags), table field writes and
primitive/function-typed table reads, non-nullable array/table/class
class fields with per-construction fresh defaults, nested primitive
arrays, function arrays, function expressions and block-level functions
with closure capture (cell lowering), nested and nullable function
signature types, imported-class arrays, `std/table.keys`, and the
shared `$DealRt.Table` class that carries table values across module
boundaries.

## JVM applicability policy

Backend-neutral frontend expectations are fully enforced before any backend
executes. A JVM case is applicable when its fixture lists `"jvm"` in
`backends` (single-module adapter) or is a multi-module fixture (JVM-only by
schema). The only skips in `BackendConformanceTest` are toolchain-availability
skips (`javac`/`java` missing); there are no per-failure or unclassified
skips, and every known-failure names its follow-up issue. LuaJIT cases are
never weakened by the JVM gate.

## Promotion instructions

When one of the tracked issues lands:

1. the gate starts failing with a `STALE known-fail` message naming the
   fixture — this is the promotion signal, not a regression;
2. replace `@expected: known-fail MODE` with `@expected: MODE` (drop the
   `@issue` tag) in the named `.deal` fixture, or drop the `"knownFail"`
   field in the named JSON case;
3. re-run `./run_tests.sh`; the fixture must now pass as a real v1.2
   conformance test.
