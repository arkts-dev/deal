# DEAL v1.2 Conformance Promotion Gate (ISSUE-0107)

`fs/docs/spec-v1.2.md` is the only language spec for DEAL v1.2. v1.1 source
compatibility is not preserved: rest parameters, top-level executable
statements, imports after declarations, and nested exports are removed, `int`
becomes signed 32-bit, and `bytes` plus the C FFI declaration surface
(`// @deal-version`, `// @extern-c`, `// @c-struct`, `// @c-pointer`) are added.

This document records how the conformance gate enforces the promotion and
which v1.2 cases remain intentionally unsupported (each with an explicit
failing fixture and a tracked follow-up issue).

## The three gates

| Gate | Runner | Must hold |
|---|---|---|
| Frontend conformance (v1.2 grammar and semantics) | `deal.test.ConformanceTest` over `test/conformance/frontend/` | every fixture passes; 0 failed; 0 skipped |
| LuaJIT backend-runtime conformance (v1.2) | `deal.test.ConformanceTest` over `test/conformance/backend-runtime/` (real LuaJIT execution) | every fixture passes; 0 failed; 0 skipped |
| JVM backend-runtime conformance (v1.2) | `deal.test.BackendConformanceTest` (`test/conformance/fixtures/*.json`, `backends: ["jvm"]`) plus `deal.test.JvmBackendTest` | every JVM-applicable case passes; 0 unclassified skips |

## Classification contract

Every `.deal` file under `test/conformance/` carries an explicit
classification. There are no unclassified skips:

- a file without `@expected`, with an unknown `@expected` value, or with a
  `@spec` reference that does not start with a v1.2 spec section is a
  **classification failure** and fails the gate;
- `compile-ok` / `compile-error CODE` — frontend-only expectations;
- `runtime-ok` / `runtime-error CODE` — compile plus real LuaJIT execution;
- `companion` — classified support module (`*_lib` fixtures) that must keep
  compiling standalone; `.d.deal` companions run the declaration-file
  pipeline (`ExportExtractor`);
- `host-fixture` — reserved for `test/conformance/host-fixtures/*.d.deal`
  (discovery skips that subtree; the classification is documented in each
  file);
- `known-fail MODE` — an explicit failing fixture for an intentionally
  unsupported v1.2 case, with a mandatory `@issue` tag.

The `known-fail` mechanism is the promotion driver: the runner executes the
underlying expectation and records the case as a non-fatal tracked
known-failure while the requirement is unsatisfied. As soon as the tracked
issue lands and the fixture starts passing, the gate **fails with a
promotion instruction** (remove the `known-fail` marker and set the real
`@expected`), so v1.2 promotion is forced instead of silently forgotten.
The JSON backend fixtures use the same mechanism via the `"knownFail"` field.

### Staged failures (design-sanctioned interim states)

A staged failure is a fixture whose own expectation is temporarily
unsatisfied by a locked artifact whose disposition is owed by another
child; it is tracked by the runner's staged-failure registry, never by a
fixture `@expected` value. The runner executes the fixture, verifies that
the locked artifact code is still produced, and records the case as a
non-fatal `STAGED-FAIL` naming its owning issue. The registry is
validated against the on-disk corpus every run, and an entry that becomes
stale fails the gate with a promotion instruction (remove the registry
entry) — the staged state can never silently rot.

- `test/conformance/backend-runtime/stdlib-edge/time-now-millis-positive.deal`

## JVM corpus promotion gate (ISSUE-0102 origin — ISSUE-0168 capability accounting)

`deal.test.JvmConformanceTest` runs every existing backend-runtime
conformance test through the real whole-project pipeline (module
discovery → frontend → `JvmBackend` codegen → `javac` → `java`) with a
deterministic applicability policy:

- frontend-classified files (`compile-ok` / `compile-error`) run the
  shared frontend pipeline and must pass 100%;
- companions compile as part of their importing tests' module graphs
  (never counted separately);
- known-fail fixtures run through the pipeline and stay tracked while
  their underlying mode fails (a stale marker fails the gate with a
  promotion instruction);
- backend-runtime tests are JVM-applicable unless the explicit skip
  registry classifies them. Every skip carries a documented reason and
  a gap id. The ISSUE-0168 capability-accounting re-audit promoted 50
  previously-skipped cases (the async-await and @jsonable slices that
  landed after the ISSUE-0102 gate, plus `async-cross-module` via the
  explicit-`.deal` companion alias fix) and classified the 34 remaining
  failures under the active gap ids, each probed through the real
  pipeline every run:
  - `JVM-GAP-STDJSON` — std/json JVM boundary: `JvmBackend` E6000 at
    `import std/json` (13 tests);
  - `JVM-GAP-JSONABLE-RESIDUAL` — residual @jsonable JVM defects
    (4 tests);
  - `JVM-GAP-HOST-ABI-SHAPES` — JVM host ABI unsupported declared
    shapes (16 tests, including the host async export used as a
    function value, relabeled from JVM-GAP-XMOD-FNVALUE with the
    shared-carrier lane);
  - `JVM-GAP-ASYNC-FNEXPR` — retired (ISSUE-0304,
    `jvm-v12-async-expressions` D1-D3): async function expressions emit
    through the sync closure machinery with the async descriptor marker

    cell + anonymous-wrapper path, and the discard-position await
    statement evaluates exactly once with the completion check — the
    two fixtures (async-fn-expr.deal, async-await-statement.deal) pass
    the real pipeline and the stale-skip gate forced the registry
    entries out;
  - `JVM-GAP-DEFAULTS-PLANS` — the v1.2 default-plan lane
    (ISSUE-0340, LuaJIT-owned): imported non-literal defaults and the
    phase-order Error-catch probe (2 tests);

The ISSUE-0301 descriptor seam now delegates to the one canonical
descriptor service (`deal.descriptors.CanonicalRuntimeTypeDescriptor`):
`CompilationOrchestrator.codegenAllJvm` builds the per-compilation
identity index plus descriptor service exactly like the Lua arm and
threads them through `JvmBackend.generate`/`collectShapes`;
`fnDescriptor`/`typeDescriptor`/`classCheckDescriptor`/`classIdentity`
consume `encode`/identity-projection text (the builtin `Error` atom is
`@$builtin/Error`; project class atoms are
`@<configuredRootText>/<modulePathComponents>/<ClassName>` — the JVM
arm's index qualifies each module with its own checker-held path

`backend-runtime/modules/modid-class-identity.deal`; the module path is
dotted, so the produced atoms are dot-free and the legacy
`@src.models/User` spelling is never emitted). The pre-codegen shape
collection is deterministic — dependency order, then source order —
seeded only through source-ordered walks (host declarations in
import-statement order, expression types through the AST walk; no
`HashMap`/`HashSet` iteration drives output, `deterministic-diagnostics`
D4). The collection seam also builds the compilation-wide
class-declaration identity surface (canonical class identity →
declaring module path for every class of every checked project module,
in module order then source order): the entry's shared-scope wrapper
pre-registration resolves a collected shape's class reference through
it when the declaring module is one the entry does not import directly,
so a non-entry module's qualified imported-class signature still emits
its wrapper with the real declaring module's class reference and the
artifact set stays javac-clean. The `$check` function-row non-wrapper
arm raises the matcher's pinned bare message E8001 "expected function".

The registry is validated against the on-disk corpus (a stale or dead
entry fails the run); there is no fallback skip branch, and a skip that
starts passing fails the gate with a promotion instruction (remove the
registry entry) — the same forced-promotion rule that stale known-fail
markers carry. The gate requires zero applicable failures AND at least
80% of the on-disk backend-runtime denominator to pass on JVM (253/300
= 84.3% after the ISSUE-0301 promotions: 253 applicable passed, 0
failed, 47 classified skips, 0 tracked known-fails — the counts are
asserted by the runner's summary gates, not hardcoded).

The backend work the gate drove (ISSUE-0102): C-style `for` loops,
array `for-of`, `break`/`continue`, `try`/`catch`/`throw` with the
builtin `Error` reified as `DealError`, `delete`/`has()` for tables and
optional class fields (presence flags), table field writes and
primitive/function-typed table reads, non-nullable array/table/class
class fields with per-construction fresh defaults, nested primitive
arrays, function arrays, function expressions and block-level functions
with closure capture (cell lowering), nested and nullable function
signature types, imported-class arrays, `std/table.keys`, and the
shared `$DealRt.Table` class that carries table values across module
boundaries.

## JVM applicability policy

Backend-neutral frontend expectations are fully enforced before any backend
executes. A JVM case is applicable when its fixture lists `"jvm"` in
`backends` (single-module adapter) or is a multi-module fixture (JVM-only by
schema). The only skips in `BackendConformanceTest` are toolchain-availability
skips (`javac`/`java` missing); there are no per-failure or unclassified
skips, and every known-failure names its follow-up issue. LuaJIT cases are
never weakened by the JVM gate.

## Promotion instructions

When one of the tracked issues lands:

1. the gate starts failing with a `STALE known-fail` message naming the
   fixture — this is the promotion signal, not a regression;
2. replace `@expected: known-fail MODE` with `@expected: MODE` (drop the
   `@issue` tag) in the named `.deal` fixture, or drop the `"knownFail"`
   field in the named JSON case;
3. re-run `./run_tests.sh`; the fixture must now pass as a real v1.2
   conformance test.
