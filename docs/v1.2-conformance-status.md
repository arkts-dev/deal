# DEAL v1.2 Conformance Status and Release Gates

`fs/docs/spec-v1.2.md` is the only language spec for DEAL v1.2. v1.1 source
compatibility is not preserved: rest parameters, top-level executable
statements, imports after declarations, and nested exports are removed, `int`
becomes signed 32-bit, and `bytes` plus the C FFI declaration surface
(`// @deal-version`, `// @extern-c`, `// @c-struct`, `// @c-pointer`) are added.

This document records the v1.2 release gates (`./run_tests.sh` and
`./coverage.sh`), the single three-backend differential conformance gate they
run, the zero-skip classification contract, the sanctioned E6006
`FFI_UNSUPPORTED_BACKEND` rejection pin, and the pre-flip transitional states
that remain tracked until the zero-skip flip lands.

## The three-backend differential gate

The single v1.2 conformance gate is `deal.test.conformance.DifferentialGate`
(`v12-zero-skip-conformance-gate` G1, G4): it discovers
`test/conformance/` once, classifies every fixture, validates the Structured
Expectation Sidecars, executes the backend-neutral frontend corpus, runs the
Compile Diagnostic comparison, and dispatches every runtime-classified case
to all three production lanes — a case passes only when all three lanes match
their expectations exactly.

The three lanes execute in real subprocesses over the real artifacts:

- **LuaJIT lane** (`LuaLane`): real frontend → `LuaBackend` → real `luajit`.
- **JVM lane** (`JvmLane`): real whole-project pipeline (`ProjectLocator` →
  `CompilationOrchestrator` → `JvmBackend`) → `javac` → real `java`.
- **JS lane** (`JsLane`): real frontend → `JsBackend` → deployed
  `deal/runtime.js` + `std/*.js` + host modules → real `node`.

All three lanes share one Shared Lane Contract: compile with the real
frontend (a compile failure is a lane compile failure, never an execution
outcome); generate and assert real artifacts; auto-invoke each non-`$`
zero-arity exported wrapper once in declaration order with discarded return
values (no lane prints results); execute `main(): null` exactly once; await
async exports to completion; capture stdout/stderr bytes separately and
compare them byte-for-byte against the sidecar transcript; frame an uncaught
DEAL error on stdout as exactly

```text
DEAL_ERROR_CODE: <code>
DEAL_ERROR_SNAPSHOT: <canonical JSON>
```

with exit 1, where the canonical JSON follows the Canonical Error Snapshot
serialization (fixed key order `code`, `message`, `sourceFile`, `line`,
`column`, then pinned optional fields in spec order `expected`, `actual`,
`frames`, `cause`) and the sidecar's Error Expectation is the authoritative
field set (a lane emits the mandatory fields plus exactly the pinned optional
fields and suppresses every unpinned optional field).

A case verdict is pass only when every lane's preparation succeeds and every
lane's execution matches its expectation exactly. The mismatch classes are
closed: `TRANSCRIPT_MISMATCH`, `ERROR_SNAPSHOT_MISMATCH`,
`COMPILE_DIAGNOSTIC_MISMATCH`, `EXIT_CODE_MISMATCH`,
`COMPILE_REJECT_MISMATCH`, `ARTIFACT_MISSING`, `TOOL_MISSING`,
`LANE_TIMEOUT`, `PROCESS_FAILURE`, `HARNESS_DEFECT` — the first differing
byte/field is named with bounded context, there is no retry and no
expectation auto-update, and infrastructure outcomes never satisfy a case.

The backend-neutral half of the gate: every `compile-ok` fixture compiles
clean through the real frontend; every `compile-error` fixture rejects with
its exact pinned code; every `compile-error` fixture with a Compile
Expectation Sidecar is compared field-exact (code/line/column/message) via
the Compile Diagnostic contract, and must emit exactly one error diagnostic.

Both release scripts run the differential gate unconditionally:
`./run_tests.sh` and `./coverage.sh` each run the gate core suite
(`deal.test.conformance.DifferentialGateCorpusTest`) and the three-lane
corpus suite (`deal.test.conformance.DifferentialGateLanesCorpusTest`), and
`./run_tests.sh` additionally runs the lane unit suites
(`LuaLaneTest`/`JvmLaneTest`/`JsLaneTest`) — all with no tool gating; the
gate is not skipped for any tool state (G8).

## Zero-Skip Classification Contract

The classification contract (G2): every `.deal` file under
`test/conformance/` carries exactly one of these classifications — nothing
else is in the grammar:

- `compile-ok` — frontend-only expectation: the fixture must compile clean;
- `compile-error CODE` — frontend-only expectation: the fixture must reject
  with exactly `CODE`;
- `runtime-ok` — compile plus real execution on all three lanes against the
  sidecar's `runtime-ok` transcript/exit expectation;
- `runtime-error CODE` — compile plus real execution on all three lanes
  against the sidecar's `runtime-error` Error Expectation (code `CODE`);
- `companion` — classified support module (`*_lib` / `*.d.deal` fixtures)
  that must keep compiling standalone; `.d.deal` companions run the
  declaration-file pipeline (`ExportExtractor`);
- `host-fixture` — reserved for `test/conformance/host-fixtures/*.d.deal`
  (discovery skips that subtree; the classification is documented in each
  file).

Every fixture carries a valid `@spec` reference to a v1.2 spec section;
every runtime-classified fixture carries a valid three-backend Structured
Expectation Sidecar; a `compile-error` fixture with a Compile Expectation
Sidecar carries an exact `@expected` code matching the pin. There is no
`known-fail` classification, no capability-skip registry, and no
tool-absence skip in the contract: a remaining `known-fail` marker, a
remaining skip-registry entry, a missing/malformed sidecar, or a missing
`@spec` is a classification failure with a promotion/removal instruction and
fails the gate. The gate has no skip branch: its `Skipped` counter is
structurally zero.

## The E6006 `FFI_UNSUPPORTED_BACKEND` rejection pin

The sanctioned FFI divergence (corpus C6): a C FFI (`// @extern-c`) fixture
executes as its runtime mode on the capable backend (LuaJIT) and is rejected
by the incapable backends (JVM, JS) with exactly the compile-reject
diagnostic `E6006` `FFI_UNSUPPORTED_BACKEND` plus the pinned `line`/`column`
— and no artifacts are produced for the rejected module. No FFI rejection
carries any other code: the sidecar schema pins
`FFI_UNSUPPORTED_BACKEND_CODE = "E6006"` (`SidecarSchemaValidator`), and a
compile-reject sidecar with any other code is a schema validation failure.

The registration is a backend-epic obligation, not yet landed at the current
revision: `deal/diagnostics/DiagnosticCode.java` registers E6000-E6005 only
(no `E6006` yet), and the incapable-lane production emissions still raise
`E6003` at the `@extern-c` arms (`deal/codegen/js/JsBackend.java`
`rejectUnsupportedImport`; the JVM C_FFI rejection record pins the E6003 the
production JVM pipeline emits at `@extern-c`,
`deal/module/CompilationOrchestrator.java`). The E6006 registration and the
JS/JVM E6003 → E6006 migration are owed by the backend epics
(ISSUE-0276/0277/0278); until they land, the FFI divergent sidecar fixture
and the two deferred C FFI runtime coverage rows (`conformance-ffi-abi-mapping`,
`conformance-ffi-runtime-errors`) stay absent from the corpus (T14).
